## Назначение проекта  
Проект — учебный BitTorrent-клиент на Node.js, созданный для практического изучения протокола BitTorrent. Он реализует полный цикл загрузки: чтение и разбор .torrent-файла в формате bencode, вычисление info-hash, обмен с UDP-трекером для получения списка пиров, рукопожатие с пирами и последующий обмен сообщениями протокола — interested, request, piece, bitfield и have. Скачанные данные разбиваются на блоки и записываются в файл, а прогресс загрузки отслеживается по мере получения отдельных частей.
Ценность проекта — не в производительности, а в наглядной демонстрации внутренней механики протокола: как трекер выдаёт адреса пиров, как клиент запрашивает доступные блоки, как отслеживается их получение и как из частей собирается итоговый файл. Код намеренно минималистичен и служит основой для дальнейших экспериментов и доработок.

## Основные модули и их ответственность 
index.js
- Роль в загрузке: точка входа. Читает путь к .torrent-файлу из аргументов командной строки (process.argv[2]), декодирует метаданные и запускает весь процесс скачивания.
- Ключевые экспорты: модуль ничего не экспортирует. Вызывает torrentParser.open() и затем download(torrent, torrent.info.name).
src/torrent-parser.js
- Роль в загрузке: превращает сырые метаданные .torrent в структуру, по которой планируются запросы: размер, длина кусков, разбивка на блоки.
- Ключевые экспорты: open — декодирование bencode; infoHash — SHA-1 от поля info; size — общий размер в 8-байтовом буфере; pieceLen — длина куска с учётом последнего; blocksPerPiece и blockLen — разбивка куска на блоки по BLOCK_LEN.
src/tracker.js
- Роль в загрузке: получает от UDP-трекера список пиров (IP и порт), к которым затем подключается клиент.
- Ключевые экспорты: getPeers — orchestrates connect→announce и вызывает callback со списком пиров; внутренние buildConnReq, parseConnResp, buildAnnounceReq, parseAnnounceResp, udpSend собирают и разбирают UDP-пакеты.
src/message.js
- Роль в загрузке: низкоуровневая работа с протоколом — кодирование исходящих и декодирование входящих сообщений BitTorrent.
- Ключевые экспорты: конструкторы buildHandshake, buildKeepAlive, buildChoke, buildUnchoke, buildInterested, buildHave, buildBitfield, buildRequest, buildPiece, buildCancel, buildPort и parse для разбора сообщения на id и payload.
src/Pieces.js
- Роль в загрузке: учёт того, какие блоки уже запрошены и получены, что позволяет избегать дублей и определять завершение.
- Ключевые экспорты: класс с методами addRequested, addReceived, needed (нужен ли блок), isDone (всё скачано), printPercentDone (прогресс в процентах).
src/Queue.js
- Роль в загрузке: задаёт порядок блоков для запроса у пира и хранит флаг choked, разрешающий запросы.
- Ключевые экспорты: класс с методами queue(pieceIndex) (генерация блоков куска с begin/length), deque, peek, length и полем choked.
src/download.js
- Роль в загрузке: связывает трекер, очередь, учёт блоков и файловую запись в единый процесс загрузки по TCP-соединениям.
- Ключевые экспорты: download(torrent, path) — получает пиров и запускает загрузку для каждого; внутренние onWholeMsg, msgHandler, chokeHandler, unchokeHandler, haveHandler, bitfieldHandler, pieceHandler, requestPiece обрабатывают сообщения и пишут блоки по смещению.
src/util.js
- Роль в загрузке: обеспечивает стабильный peer-id клиента для handshake и announce.
- Ключевые экспорты: genId() — случайные 20 байт с префиксом -AT0001-, кэшируемые в переменной id.

## Kлючевые сущности и термины (мини-глоссарий)
- bencode — формат кодирования данных, используемый в .torrent-файлах (строки, числа, списки, словари). Декодируется в src/torrent-parser.js (open).
- info hash — SHA-1 хеш от закодированного поля info торрента; уникально идентифицирует раздачу. Вычисляется в torrentParser.infoHash.
- piece (кусок) — единица целостности данных фиксированной длины (piece length), на которые делится раздача. Обрабатывается в pieceLen и blocksPerPiece.
- block (блок) — часть куска (по умолчанию BLOCK_LEN = 16 КБ), которая реально запрашивается у пира сообщением request. Длина блока считается в blockLen.
- peer (пир) — другой участник сети, отдающий данные. Его адрес (IP + порт) получают от трекера; подключение к нему происходит в src/download.js.
- tracker (трекер) — сервер, который по info-hash возвращает список пиров. Общение с UDP-трекером реализовано в src/tracker.js (getPeers).
- announce — запрос к трекеру с info-hash и peer-id для получения списка пиров. Собирается в buildAnnounceReq.
- connection id — временный идентификатор соединения, выдаваемый UDP-трекером в ответ на connect-запрос; используется в announce. Парсится в parseConnResp.
- handshake — первое сообщение при подключении к пиру: обмен pstr, info-hash и peer-id. Собирается в message.buildHandshake.
- peer id — 20-байтовый идентификатор клиента, генерируемый с префиксом -AT0001- в src/util.js (genId).
- choke/unchoke — сигналы пира, запрещающие/разрешающие запрашивать данные. Обрабатываются в chokeHandler/unchokeHandler.
- interested — сообщение, которым клиент сообщает пиру, что хочет получать данные. Собирается в message.buildInterested.
- bitfield — сообщение, где каждый бит показывает, какие куски есть у пира. Разбирается в bitfieldHandler.
- have — сообщение о появлении нового куска у пира. Обрабатывается в haveHandler.
- request — запрос конкретного блока (index, begin, length). Собирается в message.buildRequest, отправляется в requestPiece.
- piece (сообщение) — ответ пира, содержащий данные блока. Обрабатывается в pieceHandler, записывается в файл.
- peer-id / info hash — см. выше; оба передаются в handshake и announce.


## Правила работы ассистента
- На каждый запрос пользователя предлагать более подходящую, на взгляд ассистента, формулировку промпта (улучшенную/уточнённую).
- Запрещено додумывать, предполагать от себя без явного указания пользователя
- Перед любыми изменениями должен быть предоставлен план изменений c обоснованием
- Вносить изменения только после явного разрешения пользователя
- На каждый запрос пользователя о изменениях в код задавай уточняющие вопросы
- При неопределенности со стороны пользователя уточни, что он хочет, и предложи возможные варианты

## формат ответа ИИ:
Выбор формата по типу запроса:
- Проверка валидности — есть конкретная ошибка (файл, строка, вывод/падение).
- Проверка гипотезы — есть предположение о причине, которое нужно проверить.
- Поиск решения — открытая задача, выбор из альтернатив.
- Объяснение концепции — вопрос «как устроено/зачем», без задачи менять код.

Когда пользователь просит найти решение:
  Сначала уточни у пользователя (вопросы к нему):
    - Проблема/цель — что нужно решить.
    - Контекст и ограничения — если пользователь не дал информацию, предложи контекст и ограничения сам.

  Затем в ответе, для каждого предложенного решения, приведи (шаблон ответа):
    - Проблема/цель — что решаем, в 1–2 предложения.
    - Контекст и ограничения — что уже сделано, что нельзя менять.
    - Варианты (2–5 шт.) — каждый с кратким «как работает» и плюсами/минусами.
    - Сравнение — по критериям (простота, риск, совместимость, производительность).
    - Рекомендация — какой вариант выбрать и почему.
    - План действий — шаги для выбранного варианта.
    - Проверка — как убедиться, что решение работает.
    - Решение — что применить по умолчанию, если не скажешь иначе.

Если идёт проверка валидности:
 - Имя файла и строка.
 - Причина.
 - Что сломалось — фактическое поведение (ошибка/вывод/падение) против ожидаемого.
 - Фрагмент кода/контекст — строка-две вокруг проблемы.
 - Варианты исправления (2–5 шт.).
 - Приоритет вариантов — какой рекомендован и почему.
 - Влияние на другие места — не сломает ли исправление соседние модули/тесты.
 - Риски вариантов — чем рискуем при каждом способе.
 - Как проверить исправление — конкретный тест/команда, подтверждающая валидность.
 - Выбор/решение — что применить по умолчанию.

Если идет проверка гипотезы, формат ответа
 - Гипотеза.
 - Что сработает.
 - Что не сработает.
 - Примеры (2–4 шт.).
 - Критерий подтверждения/опровержения — как отличить «верна» от «не верна» (не только зелёные тесты, но и ожидаемый конкретный результат).
 - Данные/входные условия — на чём проверяем (входные параметры, фикстуры, мок-данные).
 - Риски и побочные эффекты.
 - Измерение — как количественно оценить эффект (метрики, %, время).
 - Контр-гипотеза — альтернативное объяснение, которое тоже стоит проверить.
 - Минимальный воспроизводимый сценарий — как повторить проверку в изоляции.
 - Проверка — должна быть подтверждена зелёными тестами, если применимо.
 - Вывод/решение — что делаем по результату (принимаем, отклоняем, дорабатываем).

Если идет объяснение концепции
 - Суть (2–5 предложений): назначение, идея, где применяется — общими словами.
 - Примеры (2–4 шт.): конкретные иллюстрации концепции.
 - Интеграция: как встроить в текущий проект, пошаговые действия.
 - Последствия: что изменится/чего ожидать.
 - Ограничения: где не работает, чего нельзя делать.

## Примеры решения задач

### Рефакторинг

Исходное состояние
- somemodule.js
- somemodule.test.js

Целевое состояние
- somemodule/index.js — бывший somemodule.js
- somemodule/somemodule.test.js
- каждая отдельная функция хелпер распологается в своем файле, методы из класса не выноси

### Добавление новой функциональности
- Для модуля создаётся отдельная папка.
- Функции и классы имеют минимальную ответственность. Используй SRP

Плохо
export const someGodFunction = () => {
  const getUsers = () => { /* some code */ }
  const playMusic = () => { /* some code */ }
  const makeMove = () => { /* some code */ }
  const makeFun = () => { /* some code */ }
  const shakeBody = () => { /* some code */ }
}

Хорошо
export const getUsers = () => { /* some code */ }
export const playMusic = () => { /* some code */ }
export const makeMove = () => { /* some code */ }

const makeFun = () => { /* some code */ }
const shakeBody = () => { /* some code */ }

export const withFun = () => {
  const fun = makeFun()
  const shake = shakeBody()
  return { fun, shake }
}

### Добавление тестов

Задача: добавить unit-тесты для src/message (конструкторы сообщений и parse).

Плохо
// test/all.test.js — все модули в одном файле, одна «бог-функция» на всё
const message = require('../src/message')
const Pieces = require('../src/Pieces')
const tracker = require('../src/tracker')

test('всё работает', () => {
  expect(message.buildHandshake({ info: {} }).length).toBe(68)
  expect(message.buildChoke().readUInt8(4)).toBe(0)
  expect(new Pieces({ info: { pieces: Buffer.alloc(40) } }).isDone()).toBe(false)
})

// src/message/message.test.js — без моков зависимостей: тест зависит от окружения
const message = require('./index')

Хорошо
// src/message/message.test.js — тест рядом с модулем, зависимости замоканы, один describe на функцию
jest.mock('../torrent-parser', () => ({ infoHash: jest.fn(() => Buffer.alloc(20, 1)) }))
jest.mock('../util', () => ({ genId: jest.fn(() => Buffer.alloc(20, 2)) }))

const message = require('./index')

describe('message builders', () => {
  test('buildHandshake', () => {
    const buf = message.buildHandshake({ info: {} })
    expect(buf).toHaveLength(68)
    expect(buf.toString('utf8', 1, 20)).toBe('BitTorrent protocol')
  })

  test('buildChoke', () => {
    expect(message.buildChoke().readUInt8(4)).toBe(0)
  })
})

describe('message.parse', () => {
  test('keep-alive', () => {
    expect(message.parse(Buffer.alloc(4)).id).toBeNull()
  })

  test('request', () => {
    const p = message.parse(message.buildRequest({ index: 1, begin: 0, length: 16384 }))
    expect(p.id).toBe(6)
    expect(p.payload.index).toBe(1)
  })
})

// Новый модуль — в отдельной папке, тест рядом
// src/pieces/index.js + src/pieces/pieces.test.js

- тест лежит рядом с модулем и называется <модуль>.test.js;
- зависимости (сеть, нативные модули, соседние модули) мокаются;
- один describe на экспортируемую функцию, один test на конкретное поведение;
- новый модуль — отдельная папка с собственным тестом, а не общий test/all.test.js.
